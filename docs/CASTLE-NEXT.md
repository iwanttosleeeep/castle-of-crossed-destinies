# Castle 下一版：让不同的解释真正相遇

2026-09-20 · 产品与实现建议，尚未实施

## 产品定位

Castle 是一间让已有命理报告相互质询的私人阅读室。首批用户是已经拥有一两份报告、喜欢探索不同解释、愿意使用自己 API Key 的人。

首页建议表达：

> 同一个你，为什么会被命运讲成不同的故事？
>
> 带来一至七份报告。先听各自的解释，再看它们在哪里相遇、分歧，以及哪些问题仍由你决定。

先提供「旁听一场示例庭审」和「带我的报告入场」。示例使用明确标注的虚构资料和预制文本，无需 Key，也不实时调用模型。它要展示完整的一次阅读、分歧与追问，而不只是展示七张空卡片。

完整七体系保持可用。首次体验建议选择两至三份自己已有的报告；单份也可阅读，跨体系审议需要至少两份成功报告。市场是否接受这一体验尚待真实用户验证。

## 从现有实现发现的问题

| 现状与证据 | 用户受到的影响 | 下一版行为 |
| --- | --- | --- |
| `frontend/src/App.tsx` 默认选中七体系；首页写「上传七套报告」 | 容易以为必须集齐七份 | 上传哪些就启用哪些；明确一份可开始、两份可比较 |
| `startCase` 等所有顺序上传完成后才设置案件数据 | 中途失败时已创建案件和上传成果不易找回 | 建案后立即显示并保存恢复入口；逐份更新状态，可继续未完成上传 |
| 确认页平铺所有字段，最多每体系 80 条 | 用户在看到价值前承担大量校对工作 | 先展示核心配置摘要与可定位的疑点；全部字段可展开、可修改；不能把模型自评置信度当可靠性证明 |
| `main.py:create_reports` 等所有报告和 Tribunal 完成才一次保存 | 某室先完成也看不到；进程中断前没有逐室成果 | 每室完成即保存与呈现；可仅重试失败室、单独重试 Tribunal |
| 七室初稿要求每篇 900–1600 字，页面先铺全部正文 | 比较与追问被埋在大量阅读之后 | 显示每室短证词与可展开完整报告；多室完成后把审议摘要放到显眼位置 |
| 质询对所有室执行回答、rebuttal，再总结 | 七室全成功的一轮需 15 次模型调用，且阶段串行等待 | 用户选两三位与问题相关的发言者；保留邀请全部体系的选项；各阶段逐步显示 |
| Tribunal 只生成一篇自由文本 | 难以定位「谁与谁在哪句话上矛盾」 | 比较卡片展示原文片段、出处和关系类别，并可直接发起追问 |
| 修改事实会清空报告和 Tribunal，但保留旧庭审 | 新资料与旧结论可能混在一起阅读、导出 | 事实、报告、庭审绑定版本；历史庭审明确显示所属版本 |
| 主视觉使用绝对定位封面图 | 当前约 812px 宽预览里图片遮挡标题 | 修正平板与窄桌面断点；保留紫色、纸张与手写字体风格 |

补充小问题：报告页补填 Key 的字段以 `!apiKey` 控制显示，输入首字符后就会隐藏；Markdown 目前不完整支持链接、表格和嵌套列表；界面缺少获取报告的网站与样例格式入口。这些应随对应页面一起处理。

## 核心体验

1. **入场**：先旁听虚构示例，或上传自己已有的报告。上传界面提供清楚的格式例子与报告获取指引。
2. **核对**：核心盘面先读得懂，疑点可追溯到原文；支持展开全部字段。无需重新要求填写姓名、生日和地点。
3. **密室**：各室仅收到本室确认资料，独立生成初稿；先完成的先呈现。人物设定通过名称、措辞和关注点体现。
4. **宴会厅**：展示几条最值得读的相似处和分歧，完整报告随时展开。没有真实矛盾时如实显示，不为戏剧性强造冲突。
5. **质询**：点击一条分歧或自行提问，选择参与者。独立作答后针对具体说法回应一次，主持人说明哪些立场保留、哪些收窄。
6. **带走**：沿用 Markdown 导出和案件恢复；新增轻量收藏或个人备注时，将用户的生活反馈明确标记为用户陈述。

如果用户入场时已填写一个问题，初始综合报告仍只接收盘面与统一任务；该问题在质询阶段使用，避免把所有初稿预先引向同一主题。

## 怎样既好读又有依据

继续采用已经让项目成功运行的轻量 Skill。完整正文自然表达，原七套知识包继续作为归档。下一步加强资料引用和对话行为，不把全文重新塞进复杂 JSON 契约。

比较卡片可用一个小型附加索引：所属报告版本、原文片段、类别、比较说明。程序核验片段确实存在于原报告；索引失败仍可显示正文。程序能证明片段存在，不能仅凭字符串校验证明解读正确。

「真正冲突」至少要谈同一问题、相近条件和时间范围。例如，一个体系讨论长线规划，另一个讨论短期决策节奏，不宜直接标成对立。需要具体指向原文，不能只靠模型填一个冲突标签。

角色的区别也应体现在追问方式：八字关注季节与结构，紫微关注角色与宫位关系，西占关注结构张力，印占关注时间层，人类图关注可观察的决策尝试。它们不能据此添加输入没有的盘面。

七室使用同一语言模型，输入隔离并不使它们成为七个独立的知识来源。因此用「叙事相似」「不同解释」呈现，不做七票多数即真的结论，也不承诺量化准确率。

## 实现顺序与验收

### 第一批：可靠完成一次使用

- 报告、质询改为有状态任务；按步骤保存。前端轮询即可先交付，流式文字可后加。
- 每个任务保存事实版本与模型配置；同版本重复点击不重复启动同一任务。
- Key 只在执行期间内存持有；进程重启后保留已完成结果，未完成部分请求用户重新提供 Key，不承诺无人值守跨重启续跑。
- 建案成功即保留恢复入口，浏览器恢复能力与服务端保存分开设计；Key 不写入持久存储。
- 一室失败不覆盖其他成功报告；全部失败不能标成报告完成；更新事实后明确区分历史庭审。
- 修复标题遮挡、Key 输入和 Markdown 展示。

验收：模拟一个慢室、一个失败室、刷新页面、重复点击和事实更新；验证成功成果保留、失败可重试、版本不混用。请求耗时需真实服务测量，不能以模拟测试估计。

### 第二批：让人迅速看懂为什么值得用

- 虚构示例庭审，无文件、无 Key 即可完整旁听。
- 上传启用体系、重点核对、短证词加全文、清楚的步骤导航。
- 宴会厅比较卡片、点选参与者、一次有对象的 rebuttal。
- 恢复案件、导出、结束庭审放到自然易找的位置。

验收：请 5–8 位已拥有报告的试用者自行操作。观察是否能理解入口、到达审议、指出一条具体分歧并提出自己的追问；记录阻塞原因与用时。以这些观察决定继续开发，而不拿「觉得准」作为成功指标。

### 第三批：按实际需求引入排盘

计算引擎作为可选资料来源，与上传报告产出同一份确认资料。需要出生资料的自动排盘入口单独设计；上传用户仍无需填写这些字段。

先用已有真实报告核对一套引擎的普通案例和时间边界，再选择下一套。八字和紫微是前期候选；其余体系继续用上传资料。不要因找到七个仓库就同时承担七套算法、流派约定和部署依赖。
